5. DATABASE SCHEMA (Prisma) — DESIGN RULES
================================================================================
Models required: User, RefreshToken, Product, Cart, CartItem, Order,
OrderItem, Payment, Reservation. Introduce additional models only if a real
gap appears (document the reason if so).

Enums:
  enum Role {
    ADMIN
    CASHIER
  }

  enum OrderStatus {
    PENDING     // order/cart converted to checkout attempt, not yet reserved
    RESERVED    // stock successfully reserved, awaiting payment
    PAID        // payment succeeded, order finalized
    FAILED      // payment failed, stock released
    EXPIRED     // reservation timed out, stock released
    CANCELLED   // manually cancelled (before or after payment)
  }

  enum ReservationStatus {
    ACTIVE
    RELEASED     // released due to expiry, failure, or cancellation
    FINALIZED    // consumed permanently because payment succeeded
  }

  enum PaymentStatus {
    PENDING
    SUCCESS
    FAILED
    TIMEOUT
  }

  email         String   @unique
  passwordHash  String                       // bcrypt hash ONLY — never plaintext,
                                              // never returned in any API response

  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt
  carts         Cart[]
  orders        Order[]
  refreshTokens RefreshToken[]

RefreshToken:
  id            String    @id @default(uuid())

  tokenHash     String                       // SHA-256 (or bcrypt) hash of the raw
                                              // refresh token — the raw token is NEVER

  revokedAt     DateTime?                    // null while active; set on logout,
                                              // rotation, or reuse-detection
  createdAt     DateTime  @default(now())

  @@index([userId])
  @@index([tokenHash])

Product:

WHY THESE CONSTRAINTS EXIST (Antigravity must include equivalent reasoning
in the README written in a later step):
  - User.email UNIQUE: standard login-identity guarantee; also the natural
    place a duplicate-registration conflict would be caught.
  - User.passwordHash never serialized in any API response (enforced via a
    Prisma `select`/DTO mapping, not by trusting callers to omit it).
  - RefreshToken.tokenHash (never the raw token) stored: if the database
    were ever compromised, no usable refresh token would be exposed. Raw
    tokens exist only transiently in the request/response and on the
    client.
  - RefreshToken.revokedAt nullable timestamp: makes revocation and reuse
    detection a simple, queryable state instead of physically deleting rows
    (keeping an audit trail of prior sessions).
  - Order.idempotencyKey UNIQUE: guarantees the database itself rejects a
    second "create order" attempt carrying the same client-generated key,
    even under a race, because the unique constraint is enforced atomically
    by Postgres regardless of read timing in application code.
  - Payment.orderId UNIQUE: makes it structurally impossible to attach two
    payment attempts to one order — a second attempt must update the
    existing row, not insert a new one.
  - Payment.idempotencyKey UNIQUE: protects against duplicate payment
    submissions (double-click / retry) independently of the order-level key.
  - CartItem @@unique([cartId, productId]): prevents duplicate line items for
    the same product; forces "add to cart" to become an upsert.
  - Reservation.releasedAt + status: makes release logic idempotent — the
    release routine always checks "status == ACTIVE" before transitioning,
    so running it twice (sweeper race, manual retry, restart) is a no-op the
    second time instead of double-crediting stock back.
  - Cart.userId / Order.userId: gives every cart and order a clear owner so
    authorization can be enforced with a simple, indexed equality check
    rather than trusting a client-supplied identifier.
  - Decimal instead of Float for all money fields: avoids floating-point
    rounding errors in totals.
  - OrderItem.unitPrice snapshot: preserves historical order accuracy if
    Product.price changes later.
  - Indexes on Reservation(productId, status), (status, expiresAt),
    Cart(userId, status), Order(userId, status): keep stock-availability
    checks, the expiry sweeper query, and ownership-scoped listing fast as
    data grows.

6. INVENTORY MODEL — SINGLE SOURCE OF TRUTH (READ THIS BEFORE SECTION 7)
================================================================================
This project uses exactly ONE inventory model, applied consistently
everywhere in this document, in the schema, and in the implementation:

    Product.stock == the quantity currently available to sell right now.

There is no separate "physical stock" field and no derived
"availableStock = stock - active reservations" calculation anywhere in this
system. Product.stock IS the available stock, at all times.

Consequences, applied uniformly:
  - Checkout / reservation creation: Product.stock is atomically decremented
    by the reserved quantity (Section 7).
  - Payment SUCCESS: Product.stock remains decremented (the sale is final;
    nothing changes on the product row).
  - Payment FAILURE, Payment TIMEOUT, Reservation EXPIRY, Order
    CANCELLATION (from RESERVED or from PAID): Product.stock is restored
    (+= quantity) exactly once, guarded by the reservation's
    ACTIVE -> RELEASED (or FINALIZED -> RELEASED, for post-payment
    cancellation) transition succeeding.
  - GET /api/products and GET /api/products/:id/stock simply return
    Product.stock directly — no additional subtraction step, no
    aggregation query over Reservation at read time.

Any code, comment, or documentation elsewhere in this file that appears to
suggest computing availableStock as a subtraction from active reservations
is superseded by this section. Antigravity must not implement that
alternate model.

7. CONCURRENCY-SAFE STOCK RESERVATION — REQUIRED APPROACH
================================================================================
DO NOT implement stock checks as a plain read-then-write:
    const p = await prisma.product.findUnique(...)
    if (p.stock >= qty) { ...write... }     // <-- RACE CONDITION, FORBIDDEN

REQUIRED APPROACH — atomic conditional update inside a serializable
transaction, using one of these two equivalent safe patterns:

  Pattern A (recommended, simplest to reason about — "atomic conditional
  decrement" using a single conditional UPDATE):
    Within a single Prisma $transaction:
      1. Run an atomic UPDATE that only succeeds if enough stock remains:
           UPDATE "Product"
           SET stock = stock - :qty
           WHERE id = :productId AND stock >= :qty;
         Check the affected-row count (Prisma: use $executeRaw and check
         the returned count, or updateMany + result.count). If 0 rows
         affected, the reservation attempt fails — treat as a stock
         conflict (409) for this product.
      2. Only if the UPDATE affected 1 row, insert the Reservation row and
         the Order/OrderItem rows in the SAME transaction.
      3. Commit. If any step fails, the whole transaction rolls back
         (including the stock decrement), so stock is never lost.

  Pattern B (row-lock based, use if Pattern A's raw SQL feels riskier for an
  intern assessment):
    Within a transaction, run `SELECT ... FROM "Product" WHERE id = $1 FOR
    UPDATE` (via $queryRaw) to lock the specific product row, blocking any
    concurrent transaction touching the same product until this one
    commits/rolls back. Then read stock, validate stock >= qty, decrement
    with a normal update, and insert Reservation/Order rows — all before
    releasing the lock at commit. This serializes access per-product-id,
    which is sufficient since the overselling risk is always scoped to one
    product.

CHOOSE ONE approach and apply it consistently (Pattern A is preferred for an
Express+Prisma intern assessment because it avoids manual raw locking SQL
and is easier to unit test deterministically). Document the choice and
reasoning in code comments in the checkout service and again in the README.

Restoring stock (release/expire/fail/cancel) uses the symmetric, equally
atomic operation:
    UPDATE "Reservation" SET status = 'RELEASED', releasedAt = now()
    WHERE id = :reservationId AND status = 'ACTIVE';
    -- only if the above affected 1 row:
    UPDATE "Product" SET stock = stock + :qty WHERE id = :productId;
This guarantees stock is restored exactly once no matter how many times or
from how many different call sites (sweeper, lazy check, payment failure,
cancellation) the release is attempted concurrently — see Section 9D.

Use Prisma's interactive transaction with an explicit, sufficiently strong
isolation level for checkout, payment, and cancellation operations:
    await prisma.$transaction(async (tx) => { ... }, {
      isolation: Prisma.TransactionIsolationLevel.Serializable
    })
Handle serialization failures (Postgres error code 40001) by catching them
and retrying the whole transaction a small, BOUNDED number of times
(maximum 3 attempts). If still failing after the retry budget is exhausted,
return 409 Conflict to the client rather than retrying indefinitely. Never
implement unbounded/infinite retry loops.

8. CHECKOUT FLOW — REQUIRED SEQUENCE
================================================================================
Precondition: the caller is an authenticated user (Section 13) and the
supplied cartId belongs to that user (Section 14) — checked BEFORE any of
the steps below, outside the transaction, returning 403 if ownership fails.

  1. Client calls POST /api/checkout with { cartId, idempotencyKey } and a
     valid access token.
  2. Backend validates idempotencyKey format and looks up Order by that key
     first. If an Order already exists for this key, return its current
     state immediately (200) instead of creating a new one — this is the
     idempotency short-circuit, checked BEFORE the transaction begins (see
     Section 18 for why the initial lookup alone is not sufficient).
  3. Load the cart and its items; validate the cart belongs to the
     requesting user, is ACTIVE, and is non-empty.
  4. Begin a single database transaction (Serializable, see Section 7).
  5. For each cart item, run the atomic conditional stock decrement
     (Pattern A or B). If ANY item fails to reserve, roll back the entire
     transaction — checkout must be all-or-nothing across every line item.
  6. Create the Order (userId = requesting user, status = RESERVED via the
     centralized state machine — see Section 11, which must already exist
     before this step is implemented), OrderItems (unitPrice snapshot from
     current Product.price), and one Reservation row per product with
     expiresAt = now() + 5 minutes.
  7. Mark the Cart as CONVERTED so it can't be checked out again.
  8. Commit transaction.
  9. Return the Order (with items, total, expiresAt) to the client.
 10. If step 5 fails for any item, return 409 Conflict with a message
     identifying which product(s) lacked sufficient stock; the Order must
     NOT exist in the database in this case (full rollback). If a
     serialization failure (40001) occurs, apply the bounded retry policy
     from Section 7 before surfacing 409.

The order must never claim reserved stock that the transaction didn't
actually and successfully decrement — hence steps 5 and 6 living inside the
same atomic transaction is mandatory, not optional.

Dependency note: this flow requires the Order state machine (Section 11) to
already exist, because step 6 performs the PENDING -> RESERVED transition
through it. The implementation sequence in Section 26 places the state
machine step immediately before the checkout step for exactly this reason.

9. RESERVATION EXPIRY — RESTART-SAFE DESIGN
================================================================================
Do NOT rely on setTimeout/in-memory timers as the source of truth — they are
lost on server restart/redeploy (which happens routinely on Render free
tier).

REQUIRED design — hybrid of scheduled sweep + lazy check:

  A) Persisted expiry field: Reservation.expiresAt is the single source of
     truth for when a reservation should die. No timer needs to "remember"
     anything; the database always knows.

  B) Background sweeper job (src/jobs/): a `setInterval`-driven or
     node-cron-driven job running e.g. every 30–60 seconds that:
       1. Finds all Reservations where status = ACTIVE AND expiresAt < now().
       2. For each, in its own transaction:
            - Attempt the atomic ACTIVE -> RELEASED transition (Section 7);
              if 0 rows affected, another process already handled it — skip
              (idempotent no-op).
            - If the transition succeeded, restore stock (Product.stock +=
              reservation.quantity) in the same transaction.
            - If the parent Order is still RESERVED, transition it to
              EXPIRED via the centralized state machine (Section 11).
       3. This job is safe to run redundantly / after a restart because it
          only acts on rows still ACTIVE with a past expiresAt — nothing
          depends on the process having been alive continuously.

  C) Lazy expiration on read/use: any code path that reads or acts on a
     Reservation or Order (e.g. GET /orders/:id, payment submission) must
     first check `if (reservation.status === 'ACTIVE' && expiresAt < now())`
     and, if true, run the SAME release routine used by the sweeper (extract
     it into a shared service function, e.g. `expireReservationIfDue(tx,
     reservationId)`) before proceeding. This guarantees correctness even in
     the seconds between actual expiry and the next sweeper tick, and even
     if the sweeper job were ever disabled.

  D) Idempotency of release itself: because release always transitions
     ACTIVE -> RELEASED via the atomic conditional update from Section 7,
     and stock is only restored when that transition actually affects a
     row, calling release twice (sweeper + lazy check both firing
     near-simultaneously, or a retried request) is safe — the second caller
     finds status already RELEASED, the conditional update affects 0 rows,
     and stock is NOT restored a second time. This same guard covers the
     expiry sweeper race, the payment-failure race, and the cancellation
     race uniformly, because they all funnel through the same shared
     release function.

================================================================================
10. MOCK PAYMENT & STATE TRANSITIONS
================================================================================
Endpoint: POST /api/orders/:orderId/payment (authenticated; see Section 14
for who may call this)
Body: { outcome: 'SUCCESS' | 'FAILURE' | 'TIMEOUT', idempotencyKey }

Preconditions (validated before any state change):
  - Order must exist, the requesting user must be authorized for it
    (Section 14), and it must currently be in RESERVED status (reject with
    409 if PAID/FAILED/EXPIRED/CANCELLED already — see state machine).
  - Reservation(s) for this order must still be ACTIVE and unexpired; if
    lazily found expired, run expiry first (Section 9C), then reject the
    payment attempt with 409 ("reservation expired").
  - Look up Payment by idempotencyKey first: if it already exists, return
    its existing recorded result rather than processing again (see Section
    18 for the full idempotency guarantee, including the unique-constraint
    backstop for concurrent duplicate submissions).

Behavior per outcome, all inside one Serializable transaction:
  SUCCESS:
    - Payment.status = SUCCESS
    - Reservation.status = FINALIZED for all reservations on this order
      (releasedAt is NOT set here — FINALIZED is a distinct terminal state
      meaning "consumed by a real sale", not "returned to pool")
    - Order.status = PAID (via the state machine)
    - Product.stock is NOT restored (per Section 6, the decrement made at
      reservation time already IS the final, correct deduction for the sale)

  FAILURE:
    - Payment.status = FAILED
    - Run the shared release routine (Section 7/9D) for each reservation:
      ACTIVE -> RELEASED, releasedAt = now(), Product.stock += quantity
    - Order.status = FAILED (via the state machine)

  TIMEOUT:
    - Simulate "payment never resolved." Payment.status = TIMEOUT.
    - Treat identically to a natural reservation expiry: run the shared
      release routine, Order.status = EXPIRED (via the state machine).
    - (Rationale: from the inventory's perspective, a timed-out payment and
      an expired reservation are the same event — stock must return to the
      pool either way.)

Concurrent payment submissions for the same order (e.g. a double-click
racing two POST /payment calls, with or without matching idempotency keys)
must never: create two Payment rows (blocked by Payment.orderId UNIQUE and
Payment.idempotencyKey UNIQUE), restore stock twice (blocked by the
Reservation release guard in Section 7/9D), or leave the order in two
different terminal states. If a second concurrent request loses the race
for the Payment row (P2002 on orderId or idempotencyKey), catch it, re-fetch
the now-existing Payment/Order, and return that state rather than erroring.

Mock timing: for a 72-hour assessment it is acceptable and simpler to let
the client explicitly request `outcome: 'TIMEOUT'` and have the backend
apply the TIMEOUT branch immediately, rather than building a real artificial
delay mechanism. Document this choice in the README.

================================================================================
11. ORDER STATE MACHINE
================================================================================
States: PENDING, RESERVED, PAID, FAILED, EXPIRED, CANCELLED

Valid transitions ONLY:
  PENDING   -> RESERVED
  RESERVED  -> PAID
  RESERVED  -> FAILED
  RESERVED  -> EXPIRED
  RESERVED  -> CANCELLED
  PAID      -> CANCELLED         (refund-style cancellation, still restores stock)

All other transitions are INVALID and must be rejected with 409, including
but not limited to:
  CANCELLED -> anything
  FAILED    -> anything
  EXPIRED   -> anything
  PAID      -> RESERVED / FAILED / EXPIRED / PAID(again)

Implementation requirement: build ONE centralized function, e.g.
`transitionOrderStatus(tx, orderId, allowedFromStates[], toStatus)` in
src/services/orderStateMachine.ts, that:
  - Defines the allowed-transitions map as a single constant (adjacency
    list), not scattered if/else logic.
  - Performs the update as `UPDATE "Order" SET status = :to WHERE id = :id
    AND status IN (:allowedFromStates)` and checks affected row count is 1;
    if 0, throw a typed error (InvalidStateTransitionError) resulting in a
    409 response.
  - Every service that changes order status (checkout, payment, expiry
    sweeper, cancellation) MUST call this function — never write
    `order.status = X` directly anywhere else in the codebase.

IMPLEMENTATION ORDER DEPENDENCY: this state machine must be implemented
BEFORE the checkout flow (Section 8) is wired up, because checkout's
PENDING -> RESERVED transition depends on it. See Section 26 for the
corrected step ordering.

================================================================================
12. ORDER CANCELLATION
================================================================================
Endpoint: POST /api/orders/:orderId/cancel (authenticated; see Section 14)

Rules:
  - Allowed only from RESERVED or PAID (per the state machine above).
  - From RESERVED: run the shared reservation-release routine (Section
    7/9D) for each ACTIVE reservation (restores stock exactly once per
    reservation, guarded by the ACTIVE -> RELEASED atomic transition), then
    transitionOrderStatus(RESERVED -> CANCELLED).
  - From PAID: this is a "post-payment cancellation" (simulating a
    refund/void). For each FINALIZED reservation tied to the order, run an
    atomic conditional transition FINALIZED -> RELEASED (this specific
    transition is allowed ONLY from within the cancellation routine, not
    from the general release function used elsewhere) and restore stock
    (+= quantity) only when that transition actually affects a row. Then
    transitionOrderStatus(PAID -> CANCELLED).
  - Idempotency: if the order is already CANCELLED, return its current
    state with 200 rather than erroring — cancellation-of-an-already-
    cancelled-order is a safe no-op from the client's perspective. Because
    stock restoration is always gated on the reservation-status transition
    actually succeeding (not on the order status check alone), a repeated
    cancellation call can never restore stock a second time even if it
    races with the first call.
  - Wrap the whole operation (ownership/state check + stock restoration +
    status transition) in a single Serializable transaction.

13. AUTHENTICATION & AUTHORIZATION (RBAC)
================================================================================
Authentication answers "who are you?". Authorization answers "what are you
allowed to do?". Both are enforced on the backend; the frontend may also
hide/disable UI affordances for a better UX, but that is never the security
boundary.

--------------------------------------------------------------------------
13.1 Roles
--------------------------------------------------------------------------
  ADMIN:
    - Login / logout / refresh / view own profile
    - View dashboard (Section 21)
    - Create, update, delete products
    - View products and current stock
    - View all carts/orders across all users
    - View order details, payment/reservation information
    - Cancel orders when cancellation is valid, for any user's order

  CASHIER:
    - Login / logout / refresh / view own profile
    - View products and available stock
    - Create/manage their OWN cart (create, add/update/remove items)
    - Checkout their own cart
    - Submit mock payments for their own orders
    - View their own orders and order details
    - Cancel their own orders when cancellation is valid
    - Must NOT create, update, or delete products, and must NOT access
      another user's cart or order (see Section 14 for the exact ownership
      rule and the narrow exception for Admin-initiated cancellation)

--------------------------------------------------------------------------
13.2 Account provisioning — seed accounts, not open registration
--------------------------------------------------------------------------
For this assessment, open self-registration (POST /api/auth/register) is
NOT the right approach: a POS system's staff accounts are provisioned by
whoever manages the store, not created by anonymous visitors, and an open
register endpoint would need its own role-assignment safeguards (to stop a
self-registering user from granting themselves ADMIN) that add complexity
without adding real assessment value.

REQUIRED approach: a Prisma seed script (prisma/seed.ts) that creates
exactly one ADMIN account and one CASHIER account using credentials read
from environment variables (never hardcoded), e.g.:
    SEED_ADMIN_EMAIL=, SEED_ADMIN_PASSWORD=
    SEED_CASHIER_EMAIL=, SEED_CASHIER_PASSWORD=
Passwords are hashed with bcrypt before insertion; the plaintext values
only ever exist in the local/deployment environment configuration, never in
source, logs, or the database.

An admin-only endpoint to create additional CASHIER accounts (e.g. POST
/api/auth/users, ADMIN-only, still validated with Zod and hashed with
bcrypt) MAY be added if useful for the demo, but is optional — do not treat
it as required scope. Do NOT implement public self-registration.

--------------------------------------------------------------------------
13.3 Password handling
--------------------------------------------------------------------------
  - Hash with bcrypt/bcryptjs (cost factor 10-12) before storing.
  - Never store, log, or return plaintext passwords.
  - Never include passwordHash in any API response — enforce this with an
    explicit Prisma `select`/DTO mapping on every user-returning query, not
    by convention alone.

--------------------------------------------------------------------------
13.4 Access token
--------------------------------------------------------------------------
  - Short-lived JWT, expiry 15m (ACCESS_TOKEN_EXPIRES_IN).
  - Claims limited to: userId, role. No email, no password data, nothing
    sensitive beyond what's needed to authorize a request.
  - Signed with JWT_ACCESS_SECRET (from environment, never hardcoded).
  - Sent by the client as `Authorization: Bearer <token>` on every
    protected request.
  - Never logged, in either the backend or the frontend.

--------------------------------------------------------------------------
13.5 Refresh token
--------------------------------------------------------------------------
  - Longer-lived JWT or opaque random token, expiry 7d
    (REFRESH_TOKEN_EXPIRES_IN); a signed JWT is fine as long as the raw
    value is still hashed before storage (the JWT signature alone is not a
    substitute for server-side revocability).
  - The RAW refresh token is NEVER stored in Postgres — only a hash of it
    (see the RefreshToken model, Section 5). Hash with SHA-256 or bcrypt
    before persisting; compare using the same hash on refresh.
  - A user may hold multiple simultaneously-active refresh tokens (one per
    logged-in device/browser); each is independently revocable.
  - Preferred storage on the client: a secure, HttpOnly, SameSite cookie,
    so the raw refresh token is never reachable from page JavaScript. If
    the chosen frontend architecture makes an HttpOnly cookie impractical
    within the assessment's time budget, an in-memory (not localStorage)
    fallback is acceptable — document whichever choice is made and why.

--------------------------------------------------------------------------
13.6 Auth endpoints and flow
--------------------------------------------------------------------------
  POST /api/auth/login
    Body: { email, password }. Verifies bcrypt hash. On success: issues a
    new access token and a new refresh token (a fresh RefreshToken row is
    created with its hash). Returns { user (safe fields only), accessToken
    } and sets the refresh token per Section 13.5.

  POST /api/auth/refresh
    Flow:
      Client sends the current refresh token
        -> Validate its structure/signature
        -> Look up the matching RefreshToken row by hash
        -> Check expiresAt has not passed
        -> Check revokedAt is null
        -> If any check fails: 401 Unauthorized, no new access token issued
        -> If all checks pass (rotation):
             - Immediately revoke the presented refresh token
               (revokedAt = now())
             - Issue a brand-new access token
             - Issue a brand-new refresh token; store only its hash
             - Return the new access token (and new refresh token per the
               chosen storage strategy)
    This is REFRESH TOKEN ROTATION: every successful refresh invalidates
    the token that was just used and replaces it, so a given raw refresh
    token is only ever usable once.

  Refresh token reuse protection: if a refresh token is presented whose
  RefreshToken row already has revokedAt set (i.e., it was already rotated
  away or already logged out), reject with 401 and do not issue a new
  access token. Treat this as a possible token-theft/reuse signal. Keep the
  response simple for this assessment (reject the specific reused token);
  a full token-family cascading revocation system is explicitly out of
  scope — note this tradeoff in the README rather than building it.

  POST /api/auth/logout
    Revokes the current refresh token (revokedAt = now()) so it can never
    be used again. The corresponding access token is NOT separately
    invalidated server-side (JWTs are stateless) — it simply expires
    naturally within its short 15m window. This is a standard, accepted
    tradeoff of short-lived access tokens and is fine to document as-is.

  GET /api/auth/me
    Requires a valid access token. Returns the authenticated user's safe
    profile fields (id, name, email, role) — never passwordHash.

--------------------------------------------------------------------------
13.7 Backend middleware
--------------------------------------------------------------------------
  - requireAuth: verifies the access token from the Authorization header,
    attaches { userId, role } to req.user, and returns 401 if missing,
    malformed, or expired/invalid.
  - requireRole(...roles): to be used after requireAuth; returns 403 if
    req.user.role is not in the allowed set.
  - Ownership checks (for cart/order routes) are implemented as an explicit
    check inside the relevant service/controller, comparing the resource's
    userId against req.user.userId, with an ADMIN bypass where the business
    rules in Section 14 call for one — not folded into requireRole, since
    ownership is data-dependent rather than a static role property.

--------------------------------------------------------------------------
13.8 Frontend handling
--------------------------------------------------------------------------
  - Login form posts email/password to /api/auth/login; on success, stores
    the access token in memory (e.g. React context/state, not
    localStorage) and relies on the refresh-token cookie/storage mechanism
    chosen in 13.5 for renewal.
  - API client attaches `Authorization: Bearer <accessToken>` to every
    request.
  - On a 401 caused by an expired access token, the API client calls
    /api/auth/refresh once, and if that succeeds, retries the original
    failed request exactly once with the new access token. A request must
    never be retried more than once to avoid infinite refresh loops; if the
    refresh itself fails, clear auth state and redirect to /login.
  - Logout calls /api/auth/logout, then clears local auth state and
    redirects to /login.
  - Protected pages/routes redirect unauthenticated users to /login.
  - Role-aware navigation shows/hides ADMIN-only links (e.g. Product
    management) based on the authenticated user's role — again, purely a
    UX convenience; the corresponding API routes independently enforce the
    same rule server-side.

--------------------------------------------------------------------------
13.9 Explicitly out of scope
--------------------------------------------------------------------------
Do NOT implement, and do not spend assessment time on: OAuth2/social login,
email verification, password reset flows, multi-factor authentication, a
full identity-provider system, or token-family cascading revocation beyond
what 13.6 describes. These add real-world value but not assessment value
here, and the brief explicitly asks for a simple, appropriately-scoped
implementation.

14. CART & ORDER OWNERSHIP
================================================================================
Cart ownership:
  - Every Cart has a userId set to the authenticated Cashier (or Admin, if
    Admin is ever used to operate the POS directly — permitted but not the
    primary flow) who created it via POST /api/carts.
  - Every cart-scoped route (GET/POST/PATCH/DELETE under /api/carts/:id...)
    must load the cart, then verify cart.userId === req.user.userId before
    proceeding; a mismatch returns 403, not 404 (returning 404 would be
    equally acceptable to avoid confirming the cart's existence to a
    non-owner — pick one behavior and apply it consistently; 403 is
    recommended here since carts aren't otherwise sensitive/enumerable).
  - ADMIN does not need general cart-browsing access for this assessment's
    POS workflow (carts are a checkout-in-progress workspace, not a
    reporting object); Admin's read access is centered on Orders instead
    (below). If Admin cart visibility is later found necessary, add it as
    an explicit, documented exception rather than a blanket bypass.
  - A Cashier can never access another Cashier's cart by guessing or
    supplying a different cart UUID — ownership is checked server-side on
    every request, never inferred from the frontend's current navigation
    state.

Order ownership:
  - Every Order has a userId set to the Cashier who performed the checkout
    that created it.
  - GET /api/orders (list) returns only the requesting user's own orders
    for a CASHIER; an ADMIN request to the same endpoint returns all
    orders (or accepts an optional filter, e.g. ?userId=, for an admin to
    scope the view) — implement the role branch explicitly in the service
    layer, not as a client-supplied flag.
  - GET /api/orders/:id, POST /api/orders/:id/payment: allowed if
    req.user.userId === order.userId, OR req.user.role === 'ADMIN'.
  - POST /api/orders/:id/cancel: allowed if req.user.userId ===
    order.userId, OR req.user.role === 'ADMIN' — this matches the
    assessment brief's requirement that Admin can cancel orders when
    cancellation is valid, while a Cashier can only cancel their own.
  - These checks happen in the service layer (not only the controller) so
    they cannot be bypassed by any alternate code path that calls the same
    service function directly (e.g. from the expiry sweeper's internal
    calls, which operate as a trusted system actor and are exempt from
    per-request ownership checks by design, since they're not driven by an
    end-user HTTP request).

    422  schema validation failure

18. IDEMPOTENCY — IMPLEMENTATION DETAIL
================================================================================
Idempotency is enforced in three layers, and all three are required — no
single layer is sufficient on its own:

    1. Initial lookup  (fast path, but not race-safe alone)
           |
    2. Inside the transaction (business logic proceeds only if step 1 found
       nothing)
           |
    3. Database UNIQUE constraint  (the final, always-correct backstop)

Why all three: if two identical requests (same idempotencyKey) arrive
close together, BOTH can miss the initial lookup in step 1, because neither
has committed yet when the other reads. Relying only on the lookup would
let both proceed and attempt to insert. The UNIQUE constraint on
Order.idempotencyKey / Payment.idempotencyKey is what actually guarantees
correctness in that race: only one INSERT can succeed; the other raises a
Postgres unique-violation, surfaced by Prisma as error code P2002.

Required handling of P2002 on idempotency keys:
  - Catch it specifically (check `error.code === 'P2002'` and the
    conflicting field).
  - Re-fetch the row that won (by the same idempotencyKey).
  - Return that existing resource's current state to the caller as if this
    request had found it on the initial lookup — never surface a raw 500
    or a generic conflict for this specific, expected case.
  - Do not create a duplicate Order or Payment under any circumstance.

Idempotency keys are generated on the FRONTEND at the moment the user
initiates checkout / initiates payment (e.g. a UUID stored in component
state so retries of the same user action reuse the same key; a fresh
checkout attempt generates a new key). Frontend disabling the submit button
during an in-flight request is implemented too, but explicitly documented
as a UX nicety, not the source of correctness — the three-layer mechanism
above is.
